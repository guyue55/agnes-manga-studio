# 09 · 原著解析 → 故事圣经（Story Bible）：设计与落地

> 目标（用户原话）：「故事脚本页可以通过粘贴或上传故事/小说，**彻底分析、解析**获取所有需要的信息，
> 反向推动和提高剧本、资产、分镜脚本等的生成和完善，乃至抽取所有需要的**信息卡、剧情卡、资产库、地点卡**，
> 提高创作的能力、一致性」。
>
> 本文是这一能力的**设计依据 + 分批落地记录**。所有"竞品怎么做"的判断都来自
> `08-src-01…05` 五份逐包研读（源码级证据），不引用二手转述。

## 1. 先看竞品做到了哪一步（决定我们该补什么）

| 能力 | 04 号包（小说章节转剧本） | 02 号包（短剧工作台） | 05 号包（Seedance 导演台） | 我们（批 8 之前） |
|---|---|---|---|---|
| 粘贴小说原文 | ✅（上限 1 万字，超出**直接截断**） | ❌（粘贴的是"创意"） | ❌ | ✅ 粘贴，但只能整段塞进提示词 |
| 抽取实体 | 仅 `characters[{name, identity}]` + `mainPlot` | ❌ | ❌ | ❌ |
| 人物库/资产库 | ❌（不落库，只在内存里过一手） | ✅ 人物库（外貌/参考图/强制每幕出现） | ❌ | ✅ 角色档案（R14/R15） |
| 地点卡 / 道具卡 / 剧情卡 | ❌ | ❌ | ❌ | ❌ |
| 一致性载体 | ❌ | 外貌字符串 + 参考图 | `memory{locked, decisions, avoid, openQuestions}` + `constraints` | 外貌锁定 + 注入（R15） |
| 草稿持久化 | ❌ **全包零持久化，刷新即全丢** | 部分（断点恢复） | ❌ | ❌（原文只存在于输入框里） |
| 长文分块 | ❌（截断，不是分块） | ❌ | ❌ | ❌ |

**结论**：`人物卡 / 地点卡 / 道具卡 / 剧情卡` 这套"故事圣经"在五个参考包里**没有任何一个实现**，
04 号包只做到"两个字段 + 一次调用 + 截断 1 万字"。所以批 8 不是抄，而是**把 04 号的两段式往前推一整步**：
从"两个字段"推到"六类卡片"，从"一次调用"推到"分块 map + 全局 reduce"，从"截断丢字"推到"覆盖多少如实上报"。

同时明确**继承**三条已验证的机制（不重新发明）：
1. **两段式「抽取 → 就地确认 → 生成」**（04 号，批 4 已落地为 `scripts.js` 的生成前门禁）；
2. **人物卡 → 资产库 → 参考图 → 分镜注入**（02 号，批 3 已落地为 R14/R15）；
3. **一致性记忆（锁定项/已确认决定/明确不要）**（05 号的 `memory`，我们落到人物卡 `appearance` + 锁定位）。

## 2. 数据模型

### 2.1 两张新表（`lib/store.js` 的 `COLLECTIONS`）

```
story_sources  原文（一部原著一行）
  id, project_id, title, text, chars, covered_chars, truncated,
  chunk_count, status(analyzing|extracted|failed), card_count, failed_chunks,
  merged_count, error_message, model, created_at, updated_at, finished_at

story_cards    卡片（六类共用一张表，kind 判别）
  id, kind(world|character|location|prop|plot|timeline), name, summary, aliases[],
  <各类业务字段>, evidence[](块号), mentions, chunk_index, order,
  origin(chunk|bible), source_id, project_id, edited, created_at
```

**为什么六类共用一张表**：六张同构小表会把"按类取、按类渲染、按类删、按类导"写六遍，
加一类（比如"势力卡"）还要动 schema 与迁移。`kind` 判别 + `lib/story.js` 的 `CARD_FIELDS` 白名单，
用一张表换来了"加一类只改一个常量表"。

**原文为什么必须落库**：这是 04 号包被点名批评的最大缺陷（研读报告 §3.4）——
"刷新 = 粘贴的 1 万字 + 手改的人物全丢"。我们把它做成 `story_sources`，
列表接口只回传 `preview`（前 120 字），单条接口才回全文。

### 2.2 卡片字段白名单（`CARD_FIELDS`）

每类只留"下游真的会用到"的字段，而不是照抄模型给的键：

| kind | 中文名 | 业务字段 | 下游消费者 |
|---|---|---|---|
| `world` | 信息卡 | genre / tone / worldview / theme / logline / mainline | 故事构思、分集大纲 |
| `character` | 人物卡 | identity / appearance / outfit / personality / role / gender / age | 资产库、分镜注入（一致性） |
| `location` | 地点卡 | atmosphere / region / time_of_day / features | 分镜场景描述、图片提示词 |
| `prop` | 道具卡 | owner / usage / features | 分镜画面描述 |
| `plot` | 剧情卡 | stage(起承转合) / conflict / turn / outcome / involved | 单集脚本、分集大纲 |
| `timeline` | 时间线 | when / order_note | 分集大纲排序 |

## 3. 解析流水线（"彻底分析"到底怎么个彻底法）

```
POST /api/story/plan      干跑：只切块 → 告诉用户"分 N 段、发 N+1 次调用、覆盖 X/Y 字"（不调模型、不落库）
POST /api/story/analyze   真跑：落库原文 → 建 job → 并发分块抽取 → 纯函数跨块合并 → 落库卡片 → 全局归并
GET  /api/story/cards/prompt   卡片 → 提示词文本（反向驱动的取用口，渲染只在服务端做一份）
POST /api/story/cards/:id/to-character   人物卡 → 资产库（幂等）
POST /api/story/cards/import-characters  批量入资产库（返回 created/skipped）
POST /api/story/reduce    单独重跑归并（改完卡片不用重烧整本抽取）
```

### 3.1 切块（`splitChunks`，纯函数）

边界优先级 **段落 → 句子 → 硬切**，永不把一句话切两半。
两条硬性不变量（selftest 有等式钉）：

1. **`covered_chars === total_chars` 当且仅当没截断**。为此每个块**自带尾随分隔符**，
   装块时不再插入 `\n` —— 否则"跨块丢掉的那几个换行"会让等式失效，
   "到底读全了没有"这个唯一可信的判据就没了（第一版就是这么写的，被 selftest 抓住）。
2. **超次数上限（默认 24 块）时 `truncated=true` 且 `covered_chars < total_chars`**，
   前端据此明确告知"本次只解析了前 N 字" —— 绝不学 04 号包"截断了却宣称已解析全书"。

### 3.2 分块抽取（`novel_extract` 模板，每块一次调用）

- 走 `jobs.js` 的队列（并发 = 设置里的 `default_concurrent_tasks`，可被请求覆盖），
  进度通过既有 SSE `batch` 事件推给前端，复用 `renderBatchBar` 那套进度链；
- 每块调用都写一条 `generation_tasks`（`note: 原著解析 第 N/M 段`），任务页可审计；
- **单块失败不拖垮全篇**：失败项记在进度链上，其余块照常抽取落库
  （正向对照实测：把这条改成"有失败就全丢"，5 条钉立刻变红）。

### 3.3 跨块合并（`mergeCards`，纯函数）

同一人物在第 1 段和第 7 段都出现是常态。合并键 = `kind::nameKey(name)`，
`nameKey` 吃掉空白/全角标点/书名号/引号差异（"林晚" = "林 晚" = "《林晚》"）。
合并规则：更长的描述取胜、空字段被补上、`aliases` 取并集、`mentions` 累加、`evidence` 记块号。

**为什么这是纯函数**：如果让模型去重，同一份输入两次运行会得到不同的卡片集，
用户改过的卡会在下一次解析后"复活/消失"。机械判断必须可复现。

### 3.4 全局归并（`story_bible` 模板，一次调用）

输入 = 合并后的卡片清单（`digestCards`）+ 原文开头 800 字 + 结尾 800 字；
输出 = 信息卡 + 6〜12 张剧情卡（按故事顺序）。
**重跑归并是替换而非叠加**（`origin='bible'` 的先删后插），
否则每点一次"重新归并"就多一份信息卡（正向对照实测：删掉这行 → 4 条钉变红）。

## 4. 反向驱动（怎么"推动剧本/资产/分镜"）

| 卡片 | 去向 | 机制 |
|---|---|---|
| 人物卡 | **资产库**（`characters` 表） | `POST /api/story/cards/:id/to-character`，`story_card_id` 溯源 + 幂等；导入后即可挂参考图、被分镜注入（R15 链路） |
| **地点卡 / 道具卡** | **分镜提示词（使用点注入）** | 分镜行绑定 `story_card_ids` → 出图/出视频时由 `finalPrompt` 统一拼进提示词（层次：内容 → 原著场景道具 → 角色 → 运镜 → 画风），跨镜头场景道具不各写各的；绑定 id 而非复制文本，改卡片即全镜头生效 |
| 剧情卡 | **分集大纲 / 单集脚本** | **一键带入**：原著页点「带入剧本」→ `#/scripts?...&bible=<id>&kinds=plot` → 服务端渲染 → `pickBibleVar` 落到 `{{本集大纲}}`/`{{剧情梗概}}`，提示条可见可撤销 |
| 信息卡 | **故事构思 / 梗概** | 同上，`kinds=world` |

关键取舍：**渲染只在服务端做一份**（`cardsToPrompt`）。前端不重复实现，
否则"回注格式"会有两个真相来源，模板变量一改就两边不一致。

| **8 补 31** | **角色（资产库）字段的唯一漏斗**：补 30 修完卡片，顺手问"同一类实体还有谁" —— 角色的 `appearance`/`outfit` 会被 `characterPhrase` **原文**注入**每一次出图提示词**，而角色表**任何一条写入路径都没有上限**（实测 POST 20000 字就存 20000 字）。更糟的是它不是一个"洞"而是 **7 个写入点各自 clip 了一部分**：`notes` 出现过 **400/400/500 三个数**，`alias` 在"人物卡导入"与"体检同步"两条路上**完全没截**（会随角色名册进每一次 LLM 请求）。修法不是"在每个写入点补一句 clip"（那正是病根），而是**只留一个漏斗**：`insertCharacter` / `updateCharacter` 两个出口，尺子在出口里，**绕不过去**；字段清单与上限表都来自 `story.js`（`CHARACTER_EDITABLE_FIELDS` / `CHARACTER_FIELD_MAX`），与人物卡**同名**的字段直接取 `FIELD_MAX` 的同一个数（同名同尺），角色独有的 `alias`/`notes` 单列并写明数字是**算出来的**（卡片别名最多 6×20+5=125，并集同步约 250 → 定 300；定 120 就会截合法数据）。前端镜像 + `maxlength`（预防）与"截断点名上报"（验收）成对。四条钉：同名同尺（selftest）、漏斗不可绕过（uitest 结构棘轮）、前后端上限表同构（uitest）、端到端截断+清空+非文本字段不被字符串化（apitest）| ✅ 已完成 |
| **8 补 32** | **AI 补分幕次（把"一格一格填"的活交给模型）**：幕次（起/承/转/合）是**分集的依据** —— `planEpisodes` 靠它在幕的收口处切集，一拍都没标就退化成"按拍数平均切"（`basis: 'count'`，切点可能落在一幕中间）。而"给 30 个拍点标幕次"是**纯分类**，正是该由模型干、不该由人一格一格填的活；体检也一直把它列为 `plot_no_stage` / `fixable: false`（"需要人拍板"）。现在 `POST /api/story/stage-fill`：先干跑回报"要补几拍、调几次模型"，确认后**一次**调用（全部拍点一次给完）补上。四条纪律：① **只补"待定"的**，人定过的幕次一个都不动；② **只认四幕词表**，脏值（"第一幕/高潮"）丢弃并如实上报，绝不落库；③ 模型可能把幕次写倒退 —— **不替它"修顺"**（那是我们编数据），只把位置报出来，且"倒退"必须按**落库后的真实状态**算（拿没落库的提议算会报假警报）；④ 返回 `basis_before`/`basis_after`，把"这次调用到底有没有用"变成可验收的证据。体检的 `plot_no_stage` 同时补上**出口**（`go` 直达原著页 `panel=outline`）—— 补幕次的按钮在那个面板里，让用户自己去找就是"只报问题、不给出口" | ✅ 已完成 |
| **8 补 33** | **AI 回原文补人物长相（找到的必须带原文原话）**：`char_no_look`（人物卡没有外貌与服装）一直挂 `fixable: false`（"需要人写"）—— 但**原著通常写了**这个人的长相，只是抽取那一步漏了。所以"回原文再找一遍"是**抽取**，不是创作；真正要防的是"模型凭名字编一个"。`POST /api/story/look-fill`：先干跑回报"要补几张、调几次"，确认后**一次**调用（每张候选卡带上**它自己那段原文**）。**核心机制是引文可验证**：模型必须交出原文里的**原话**（`quote`），服务端把它与那张卡自己的片段（去掉空白后）逐字比对，**对不上就整条丢弃并计 `ungrounded`** —— 这是"抽取"与"编造"之间唯一可机械判定的分界线，没有它，编的长相与找到的长相在数据上完全一样，而它会一路进每一次出图提示词。四条纪律：① 原文确实没写时模型回 `found:false` → 计 `not_found`（**诚实的结论**，不是失败），绝不拿编的顶上；② 引文必须来自**这张卡自己**的片段（模型把 A 的引文安到 B 头上是最容易发生也最难发现的错）；③ "原文没写 / 引文对不上 / 没给全"**三个桶分开报**（合成一个数，用户就分不清"原著没写"和"模型在编"）；④ 落库过与手改**同一把尺子**（`clipField`）。体检的 `char_no_look` 同时补上**出口**（`go` 直达原著页的人物卡）。**顺带查清一件事**：`no_source` 这条防御分支**今天不可达**（`evidence`/`chunk_index` 是来源事实、不许手改，而人物卡只由分块抽取产生；唯一没有段号的全局归并卡只产信息卡与剧情卡）—— apitest 钉的是这个**可达性**本身，将来真加了人工新建卡片的路，那条断言会红 | ✅ 已完成 |
| **8 补 34** | **把补 33 泛化成"回原文补字段"（规格驱动）+ 补场景/道具字段 + 给两个老体检项补出口**：补 33 的"补长相"与"补场景字段"是**同一件事**（每张候选卡带上它自己那段原文 → 模型交原话 → 服务端逐字核对 → 对不上就丢），照抄一份实现迟早会漂。于是抽成 `FILL_SPECS`（`char_look` / `card_inject` 两份**数据**）＋**一份**核对实现：`POST /api/story/field-fill` 用 `target` 选规格，`fillTargets`/`fillExcerpts`/`fillLines`/`applyFillAssignments` 全部按规格走。`card_inject` 覆盖地点卡（氛围/地域/时段/特征）与道具卡（持有者/用途/特征），**字段表与 `STORY_INJECT_FIELDS` 同源**（按类别取，不手抄）。落库过 `clipField`，两类**各按自己的上限**截。顺带补上两个一直"只有结论、没有出口"的体检项：`no_inject` → 原著页该类别卡片，`timeline_no_when` → 时间线卡（并**明说**这一项没有 AI 补值：时间点原文没写就只能人定）。**三个真 bug**（都由测试抓出来，见 §6.34）：① 出处条目漏带 `kind` → 字段表推成空、一个字都没写；② 路由按 `kind` 重推字段表 → "接口报 assigned=2、卡片上却一个字都没有"；③ 模板变量名对不上时 `renderPrompt` 把 `{{…}}` 换成空串 → 卡片清单**静默**发不出去，模型只能凭名字编 | ✅ 已完成 |

### 5.1 明确不做（边界）

- **原著解析做成独立页，不是故事脚本页的第 6 个页签**：`scripts.js` 的结构是"一个页签 = 一个模板 → 填变量 → 生成"，
  而解析工作台是"长文输入 + 六类卡片 + 就地编辑 + 反向驱动"。塞进 `SCRIPT_TYPES` 需要在近十处特判，
  独立页则对 `scripts.js` 零改动。跨页的"带入下一步"因此列为 8 补（需要先定模板变量契约）。
- **不做服务器端文件上传**：文件在浏览器里读成文本即可，
  原文本就要进 `story_sources`，多一条上传通路等于多一个可被外部写入的入口（与 B4 的 X2 纪律一致）。
  **`.docx` 改做（批 8 补 23），`.pdf` 仍不做** —— 原来这条写的是"docx/pdf 是另一个数量级的依赖"，
  对 PDF 成立、对 .docx **不成立**：.docx 就是个 zip，里面装一份 `word/document.xml`，
  而浏览器原生就有 `DecompressionStream('deflate-raw')`，于是零依赖就能读（自己读中央目录 + 原生解压 + 剥 XML）。
  作者的稿件绝大多数是 Word，"请先另存为 txt"这一步可以省掉。PDF 的理由换成了准确的：
  文字提取要处理字体编码/子集/CID 映射，那才是真正另一个数量级的问题。
- **不做向量检索/长文 RAG**：分块 map-reduce 已能覆盖中篇，
  RAG 需要 embedding 服务与向量库，与"本地优先、零依赖"冲突。
- **不让模型决定去重**：见 §3.3。
- **不自动导入资产库**：人物卡 → 角色是**用户的显式动作**（单条或批量）。
  自动建角色会在每次重新解析后制造重复角色，且用户没有撤销入口。

### 6.33 批 8 补 33 追加（"抽取"与"编造"之间那条可机械判定的分界线）

**A. 接着上一轮的数**：补 32 数完 `fixable: false` 的清单，剩下的判断类只剩 `char_no_look`（人物卡没有外貌与服装）
与 `no_inject`（地点/道具卡没有可注入字段）。上一轮把它们一并归成"创作、风险高"，这一轮重新问了一遍：
**"人物的长相"真的是创作吗？** 不是 —— 原著里**通常写了**，只是抽取那一步漏了。
（与 `timeline_no_when` 的关键区别：时间点原文没写就是没写、只能猜；而长相原文**有据可查**。）
于是这一趟的定性从"让模型写"改成**"让模型回去找"**，而"找"必须有据 —— 这就是引文。

**B. 机制：引文可验证**。提示词要求模型返回 `{index, found, appearance, outfit, quote}`，`quote` 是**原文里的原话**；
服务端把它与**那张卡自己**的原文片段（去掉所有空白后）逐字比对，对不上就整条丢弃并计 `ungrounded`。
这条检查是整个功能的支点：没有它，"模型在原文里找到了长相"和"模型编了一个长相"在数据上**完全一样**，
而后者会一路进每一次出图提示词，**且与写对的长相在界面上长得一模一样**。
按去空白后比对是有意的：模型常顺手在中文里加空格换行，那是格式差异不是编造 ——
**因格式差异把真找到的丢掉，等于把这项功能废掉一半**。

**C. 三个桶必须分开报**：`not_found`（原文确实没写 —— **诚实的结论**，不是失败）、
`ungrounded`（引文对不上原文 —— **那是它编的**）、`missing`/`invalid`/`empty`（没给全/编号越界/两项都空）。
合成一个"补了 N 个"，用户就永远分不清"原著没写"和"模型在编" —— 而后者才是真正要警惕的那一类。
`missing` 与 `ungrounded` 刻意**不重叠**：界面把 `missing+invalid+empty` 汇总成"另有 N 张没接住"，
同一张卡落进两个桶就会被报两遍（写断言时我把这条搞错过一次，实现是对的）。

**D. 一个只有真跑才会发现的错（假警报的反面：断言没有牙）**。第一版 apitest 的"没落库"断言写成
`listChars().filter(c => c.appearance || c.outfit).length === 0` —— 可**对照组**林晚（解析时就抽到了 `白衣`）
本来就有长相，于是这三条断言**恒为 1、永远红**。改成排除对照组之后才是真在测"这次调用有没有写东西"。
同一轮里还改了 `clearLooks()`：它一开始把 4 张全清（包括林晚），于是候选数从 3 变成 4、
"已有的一个都不动"这条钉在后续用例里就**失效**了 —— 让对照组**全程**留在名单之外，钉才在每个用例里都成立。

**E. 查清了一条不可达的防御分支**：`no_source`（这张卡没有可定位的原文出处）这条路径，
`evidence`/`chunk_index` 是**来源事实**（与 `kind`/`source_id` 同级，故意不许手改），
而人物卡只由**分块抽取**产生、必然带段号；唯一没有段号的是全局归并出来的卡，
而它只产出信息卡与剧情卡、**不产人物卡**。所以这条分支今天**不可达**。
与其编一张不可达的卡假装测过（那正是"断言因错误的原因通过"），不如把**"它不可达"本身**钉住：
apitest 断言"解析出来的人物卡全都能定位到原文出处"，将来真加了人工新建卡片的路，这条会红。

**教训**：

1. **"需要人写"里藏着"其实只要回去找"**：同一个 `fixable: false`，`no_inject`/`char_no_look` 要**写内容**，
   但"写"可以是**有据可查的抽取**（原文写了、抽取漏了）而不是**凭空的创作**。区别在于
   **能不能给出可机械核对的依据** —— 能，就把它自动化；不能，就老实留给人。
2. **给模型的输出设计一个"我们验得动"的字段**：`quote` 不只是给模型看的提示，它是**服务端的判据**。
   凡是让模型补事实类字段的地方，都该问一句"我怎么验证它没编"——答不上来就不该自动写库。
3. **"没写成"的原因要分桶，而且桶不能重叠**：分桶是为了让用户能分辨"原著没写"和"模型在编"；
   不重叠是为了让界面汇总时不会把同一张卡报两遍。两个要求同时成立才算把这件事说清楚了。


### 6.34 批 8 补 34 追加（把"回原文补字段"泛化，以及三个"成功但没写"级别的 bug）

**A. 为什么这一轮不是"再抄一个补 33"**：补 33 做完"补人物长相"，`fixable: false` 的清单里还剩
`no_inject`（地点/道具卡没有任何可注入字段）—— 它的处境与 `char_no_look` **一模一样**：
原著写了那个场景/道具，只是抽取漏了；同样"回原文找"是**抽取**而不是创作，同样可以用**引文**验证。
但两次的差别只有"问模型要什么、返回哪个键、卡片怎么称呼"——**机制完全一样**。
再抄一份的代价不是多写 80 行，而是**从此有两份引文核对**：改一处、另一处不红，直到某天有人发现
"地点卡的引文检查怎么不生效"。所以这一轮先泛化、再加功能：`FILL_SPECS` 是**数据**（两份），
`fillTargets`/`fillExcerpts`/`fillLines`/`applyFillAssignments` 是**一份实现**，都按规格走。

**B. 三个 bug，都不是"写错了"，而是"两边各判一半"**：

1. **出处条目漏带 `kind`**：`applyFillAssignments` 拿到的是 `fillExcerpts` 产出的**条目**（不是卡片），
   而"该补哪些字段"是按类别推的（`STORY_FIELDS[entry.kind]`）—— 条目没有 `kind`，字段表就是空的，
   于是**每一条都落进 `empty`、一个字都没写**。第一版就是错的，而且**症状会骗人**：
   接口报 `assigned=0`、`empty=N`，看着像"模型没给全"。真正发现它靠的是**把落库结果打出来**
   （`patch: []` 而 `offered: 1`）—— 光看汇总数字永远看不出"我们把它自己的字段表推空了"。

2. **路由按 `kind` 重推字段表**：写入循环第一版写的是 `for (const f of fillFieldsOf(spec, p))`，
   而 `p` 是**计划条目**（同样没有 `kind`）→ 字段表又空了 → **接口报 `assigned=2`，卡片上却一个字都没有**。
   这比 ① 更坏：状态码对、计数对、提示对，**只有去看卡片才知道没写**。
   修法不是"这里也记得带上 kind"，而是让**计划自己交代要写哪几个字段**（`fields`），调用方照单写。
   **正对照 JJ 一开始是绿的** —— 因为我在计划条目上顺手加了 `kind`，于是"按 kind 重推"又能工作了。
   这暴露了更本质的问题：**同一件事有了两份来源**。`kind` 在计划里**没有任何地方读**（只被显示、没被读取的
   标记等于没有），删掉它、只留 `fields`，JJ 立刻变成 5 红。**一份来源，让"绕过去"在结构上不可能。**

3. **模板变量名对不上是静默失败**：泛化时路由统一传 `卡片与原文片段`，而 `char_look` 的模板里还写着
   `{{人物与原文片段}}` —— `renderPrompt` 会把"调用方没给的 `{{…}}`"替换成**空串**，
   于是**卡片清单整个发不出去**，模型只看到一个空位置、只能凭名字编。链路上**零报错**，
   表现是"顺利路径三条断言同时红，但完全看不出为什么"。
   两处加固：**规格里记 `varName`**（模板变量名也是规格的一部分），**路由调用前先检查模板里有这个变量**，
   没有就明确报错——"模板缺变量 = 这个功能根本不可能工作"，宁可报错也不要发一个空清单。

**C. 两个"只有结论、没有出口"的老体检项**：补 33 给 `char_no_look` 补了出口，回头数一遍发现
`no_inject` 与 `timeline_no_when` 还只有结论。两者都补上 `go`，但**性质不同、说法也不同**：
`no_inject` 指向原著页的该类别卡片（那里有「AI 补场景字段」按钮），
`timeline_no_when` 指向时间线卡并**明说"这一项没有让模型补的按钮"** —— 时间点原文没写就只能人定
（补 32 的取舍：猜出来的时间线会当正史进剧本提示词，且与写错的在界面上长得一模一样）。
**出口必须落到那张卡上**：第一版只给 `kind`，浏览器契约测试立刻抓到 —— 页面能打开，但几十张卡里还得自己找，
**出口等于半个死胡同**。补 `card_id` 时又发现补 33 的 `char_no_look` **也漏了**（它当时没有浏览器契约测试，
所以一直没暴露）—— 于是加了**运行时棘轮**：对真实体检结果断言"凡是按类别落到某张卡的出口，都必须带 `card_id`"，
将来新写一个只给 `kind` 的出口会立刻红。

**D. 文案不为了共用而变含糊**：泛化最容易把**具体**的说法换成通用的说法。
第一版把 `所有人物卡都已经有外貌或服装了` 改成 `所有人物卡都已经填好了`，把
`模型没有给出可用的长相（原文里没写、或引文对不上原文）` 改成 `…可用的${label}…`。
apitest 立刻报了两条 —— 它们不是"文案变了要改测试"，而是**这句话确实变得没用了**：
前者告诉用户到底缺哪两项，后者告诉用户是"原著没写"还是"模型在编"。
所以把这两句**放进规格**（`emptyNote`/`noneNote`）：界面上的话是给用户看的，宁可每类各写一句。

**E. 教训**：
1. **"泛化"的第一价值是消掉第二份实现，不是少写代码**：两份引文核对不会立刻出错，
   会在某次只改一处时无声地错；判断要不要泛化的标准是"**机制是否相同**"，不是"代码像不像"。
2. **"成功但没写"是最难发现的一类失败**：状态码、计数、提示全都对，只有去看数据才知道没写。
   凡是"计划 → 执行"两段式的地方，计划都要**交代清楚要写什么**（这里是 `fields`），
   执行端照单写；**别让执行端按别的东西再推一遍** —— 推错的那一刻，错误会伪装成"成功"。
3. **同一件事不要有两份来源，哪怕两份都对**：正对照 JJ 变绿不是因为代码错了，而是因为**冗余**让破坏
   变得无害；冗余的东西平时不疼，只在"有人改了一处"时才发作。删掉没人读的那一份，钉才真的在管这件事。
4. **变量名/键名对不上是静默的**（`renderPrompt` 把没给的 `{{…}}` 换成空串）：
   凡是"模板 + 调用方"这种松耦合，**调用前先检查模板里有没有那个占位符**，把静默失败变成明确报错。
5. **造"旧版本"fixture、写"没落库"断言时，对照组要全程留在候选名单之外**（补 33 的教训在这一轮又用上：
   补 34 的 fixture 一开始没给 `evidence`，于是每张卡的"原文片段"都是空的、核对必然全 ungrounded）。
6. **灵敏度对照本身也会假红**：防连点那条"等 400ms 再点第二次"依赖"第一次请求还没回来、弹窗还开着"，
   机器快的时候弹窗已关、第二次点的是**摘下来的节点**（等于没点）→ 报"对照不敏感"。
   改成**确定性**的反事实：直接连发两次 `POST /api/projects`，证明**接口本身不去重**，
   于是"界面上只产生 1 个"确实来自防连点。**对照的价值在于反事实成立，不在于动作像不像真人。**

### 6.32 批 8 补 32 追加（把"该由模型干的分类"和"不该由模型编的事实"分开）

**A. 怎么找到的**：补 31 修完"角色字段"，回头数一遍**体检里那些 `fixable: false` 的项** ——
它们就是"用户必须自己动手"的清单：`no_inject`（卡里没有可注入的描述）、`char_no_look`（人物卡没有长相）、
`plot_no_stage`（剧情卡没有幕次）、`timeline_no_when`（时间线没有时间点）。
逐个问"这件事到底是**判断**还是**创作**"：`no_inject`/`char_no_look` 要**写**内容（是创作，风险高、也不好验收）；
`plot_no_stage`/`timeline_no_when` 是**分类**（给定内容、选一个标签）—— 分类正是模型的强项，也是最便宜的调用。

**B. 为什么先做 `plot_no_stage` 而不做 `timeline_no_when`**：两者都是分类，但**后果不同**。
幕次是**结构标签**（对已有拍点的分组），判错了顶多分集位置不理想，而且 `planEpisodes` 会如实报出来；
时间点（`when`）是**关于世界的事实**（"三年前"、"第二日清晨"），模型只能从上下文**猜** ——
猜出来的时间线会当作正史进剧本提示词，而**编造的时间线和写错的时间线在界面上长得一模一样**。
所以只做"结构判断"，并在提示词里写死"你只做结构判断、不创作、不新增设定"。
**教训**：同样是"用 AI 补一个空字段"，**补结构标签**和**补事实**是两件事 —— 前者可以放心自动化，
后者要先问"它凭什么知道"。宁可漏一个自动化，也不让模型往正史里塞猜测。

**C. 一次调用，不是一拍一次**：`story.stageFillLines` 把全部拍点排成一个编号清单（已有的标「已定：X」、
待定的标「待定」）**一次**交给模型。于是计费闸门就是"要补几拍"这一个数，`calls` 恒为 1。
把已有的幕次标出来是**质量关键**：模型据此知道人工划的边界在哪，补出来的幕次才会与它连成一条不倒退的线；
否则它会把整段重排一遍，把用户定好的幕次也"顺手改对"（我们不写它，但它的判断会跑偏）。

**D. 三条不能省的纪律**（都进了断言）：
① **只补"待定"的** —— 模型对"已定"的那些也会给值，一个都不许写（补 25 的人工值优先）；
② **只认四幕词表** —— `高潮`/`第一幕`/`开端` 一律丢弃并报 `not_a_stage`。脏幕次比没有幕次更糟：
`planEpisodes` 的 `stageRank` 会把它们当"没有"（rank 99），于是分集依据**看起来**标了、**实际**还是退化；
③ **不替模型"修顺"** —— 它把幕次写倒退时，只报位置，数据照写（替它修顺＝我们编数据）。

**E. 一个只有真跑才会发现的错：假警报**。`back_steps`（"幕次倒退"）第一版是拿**模型的回答**算的 ——
可模型对"已定"的那些拍也给了值，而**那些值我们根本不写**。于是 apitest 里出现了一次
"报出倒退、但那条根本没落库"的假警报（对照 IM 那一轮的经验：**假警报比不检查更糟**）。
改成按**落库后的真实状态**算（目标拍用新补的、非目标拍用原值）之后，
"该报的照报、没落库的提议不算数"两条同时成立 —— 而且**两条都要钉**：
只钉"不报假警报"的话，把检测整个关掉也是绿的（注意事项 11）。

**F. 出口**：体检的 `plot_no_stage` 此前 `fixable: false` 且**没有 `go`** —— 典型的"只有结论、没有出口"。
补上 `go: { page: 'novel', params: { project_id, source_id, panel: 'outline' } }`，
原著页认这个深链就**直接把分集大纲面板打开**（补幕次的按钮在里面，且那面板会显示"退化成按拍数平均切"的后果）。
同时**不**把它做成 `fixable: true`：补幕次要调模型、要花钱，混进"免费的一键修复"会让用户在不知情时花钱。

**教训**：

1. **"需要人动手"的清单要真的数一遍**：把体检里所有 `fixable: false` 的项列出来，逐个问"这是判断还是创作" ——
   判断类的每一件都是"用 AI 减少人工"的候选，而它们此前被一句"需要人拍板"整体跳过了。
2. **补结构标签 ≠ 补事实**：分类可以放心自动化，涉及世界设定的字段（时间点/地点/关系）先问"它凭什么知道"。
   让模型猜一个时间线进正史，比让用户自己填危险得多。
3. **报"异常"要按"最终真的会怎样"算，不是按"模型说了什么"**：拿被丢弃的提议去报异常 = 假警报。
   而且要**成对钉**（该报的 + 不该报的），否则"永远不报"也能通过。

### 6.31 批 8 补 31 追加（同一个实体的 7 个写入点）

**A. 怎么发现的**：补 30 修完卡片，接着问"同一类实体还有谁" —— 角色的 `appearance`/`outfit` 由 `characterPhrase`
**原文**注入每一次出图提示词，是比卡片更狠的下游。一查 `characterFields`：**只有 `str().trim()`，任何路径都没有上限**
（实测 POST 一个 20000 字的 `appearance` 存回 20000 字）。

**B. 但真正的问题不是"少了一句 clip"**：把 `characters` 的写入点列出来，是 **7 个** ——
① `POST /api/characters` ② `PUT /api/characters/:id` ③ 单卡导入资产库 ④ 批量导入 ⑤ 体检修复里的"入资产库"
⑥ 体检修复里的"锁定角色" ⑦ `sync_character` 同步。它们**各自 clip 了一部分字段**：
`notes` 出现过 **400（`cardToCharacter`）/ 400（`sync_character` 写死）/ 500（新表）三个数**，
`alias` 在 ③④⑤ 与 ⑦ 上**完全没截**。所以"在每个写入点补一句 clip"不是修，是**把病根再抄一遍** ——
下一个写入点照样会漏（补 30 已经证明：手抄的清单会在某次加字段时无声地错）。

**C. 修法：只留一个出口**。`insertCharacter` / `updateCharacter` 两个函数，尺子在函数体里，
**任何写入都绕不过去**；字段清单（`CHARACTER_EDITABLE_FIELDS`）与上限表（`CHARACTER_FIELD_MAX`）都在 `story.js`。
uitest 有一条**结构棘轮**：`store.insert/update('characters'` 只允许出现在漏斗那两行里 ——
将来谁再加一个写入点，只要不经过漏斗就当场变红。

**D. 同名同尺**：与人物卡同名的 7 个字段（name/role/gender/age/appearance/outfit/personality）
**直接取 `FIELD_MAX` 的同一个数**，不另定一套 —— 因为"人物卡同步到资产库"那条路本来就在用 `clip(card[k], k)`，
另定一套就会出现"卡里存得下 200 字、资产库手改被砍到 100"。selftest 钉住这条不变量。

**E. 数字要算，不要拍**：`alias` 一开始我定了 120，看着挺宽松 ——
算一下才发现**合法数据会被截**：卡片别名最多 6 个、每个 ≤20 字（`normalizeAliases`），
拼起来最长 6×20+5 = **125**；而"体检同步"会把库里已有别名与卡片别名**取并集**，两套满编约 **250**。
改成 300 才装得下。**教训**：上限不是越小越安全，**小于合法输入就是静默丢数据**；
定之前先把"最坏情况的合法输入有多长"算出来。

**F. 漏斗自身最容易被弄坏的地方**：`clipCharacterPatch` 只处理**文本**字段，其余原样带过 ——
`is_locked` 一旦被 `str()` 成 `"false"`（非空字符串）就是**真值**，用户没勾选外貌却被锁定；
`reference_image_ids` 一旦被 `str()` 成字符串，出图时就再也带不上参考图。
apitest 专门钉了这两条（布尔仍是布尔、数组仍是数组）。

**教训**：

1. **"同一个实体有几个写入点"必须真的数一遍**：补 30 学会了"数写入路径"，这一轮才发现**数量本身**就是问题 ——
   2 条路可以靠"两边都记得 clip"维持，**7 条路不行**。写入点多到一定程度，正确答案不是"每处都改对"，
   而是**让绕过去在结构上不可能**（一个出口 + 一条结构棘轮）。
2. **上限要算，不要拍**：拍出来的数看着宽松，可能已经小于合法输入（`alias` 120 < 125）。
   "更严 = 更安全"是错的，**小于合法输入就是静默丢数据**，而且丢的正是用户认真写的那部分。
3. **文本字段的归一化不能顺手用在非文本字段上**：一个 `str()` 能把布尔变真值、把数组变字符串 ——
   而且都不报错（`is_locked` 变 `"false"` 之后仍然"能用"，只是语义反了）。
   漏斗里"只动文本字段、其余原样带过"必须**显式写出来**并有断言，不能靠"顺手"。

### 6.30 批 8 补 30 追加（写入路径的两把尺子）

**A. 怎么发现的**：补 29 对完"提示词 schema ↔ CARD_FIELDS"的差集之后，顺手问了一句**下游**：
这个字段的**写入路径**有几条？一查就发现卡片有两条写入路径 —— 模型抽取（走 `normalizeCard`，被 `clip` 截到 `FIELD_MAX`）
与用户手改（`PUT /api/story/cards/:id`，把 patch **原样落库**）。同一个字段两条路两套规则，
而**两条路各自看都正常**，只有对比才看得出来。

**B. 为什么值得修**：`appearance`/`outfit` 会进 `characterPhrase`、地点/道具字段会进 `storyCardPhrase` ——
也就是说超长字段会**进每一次出图提示词**。一个几万字的 `appearance` 足以把整条出图链撑爆
（成本 + 上游拒绝），而用户以为自己只是"写得详细一点"。

**C. 最容易修坏的地方（本轮的真正风险）**：手改路径之所以原样写 `...patch`，是因为它要支持**清空** ——
`normalizeCard` 用 `if (val) card[f] = val` **丢掉空值**，而 `store.update` 是**合并**语义（键不在 patch 里就保留旧值）。
所以"改成写归一化结果"会立刻引入一个更严重的回归：**用户再也清不掉任何字段**。
正确做法是**只截断、不丢空**：空串照写。apitest 专门钉了这条回归防线。

**D. 顺手拆掉一个"第四份真相"**：`STORY_CARD_EDITABLE` 原本是**手抄的字段清单**，必须与 `CARD_FIELDS` 逐字一致 ——
漏一个字段的后果是"界面上能填、保存后静默丢失"，而且只在那一个字段上悄悄发生。现在从 `CARD_FIELDS` **推导**，
这类漂移在结构上不可能发生。

**E. 预防与验收成对**：后端截断是**验收**（数据不变式不依赖谁来写），前端 `maxlength` 是**预防**（用户不会写完再被砍）。
上限表镜像到 `consts.js`（与 `CARD_IMAGE_KINDS`/`storyCardPhrase` 同一套做法 + uitest 同构钉），
因为编辑框渲染是同步的、而这张表几乎不变 —— 镜像 + 同构钉比"为 maxlength 加一个端点"成本低得多。
真被截断时（接口调用方、或将来新增字段忘了镜像）界面会**点名说是哪个字段**。

**教训**：

1. **"同一个东西有几条写入路径"要和"有几份真相"一样认真对待**：字段表分叉我们查过了，**写入路径**分叉没有 ——
   而它的后果更重（不是显示不一致，是数据不变式只在一条路上成立）。凡是 `normalize` 类函数，都要问
   "谁还写了这张表、它走没走这里"。
2. **修"太宽松"的时候，先找出它为什么宽松**：原样写 `...patch` 不是疏忽，是**为了能清空**。
   直接换成"写归一化结果"会把一个静默超长换成"清不掉字段"，**更糟**。改之前先问"这行代码在满足什么需求"。
3. **同一个事实的两份拷贝，能推导就别手抄**：手抄的清单不会立刻出错，它会在**某一次加字段**时出错，
   而且错得没有声音（那个字段的编辑静默失效）。

### 6.29 批 8 补 29 追加（字段闭环：认识 ≠ 要过）

**A. 怎么发现的（方法可复用）**

把 `CARD_FIELDS`（系统认识哪些字段）与两个提示词的 JSON schema（向模型要哪些字段）**逐字段对差集**。
一跑就出来 6 个"从没被要过"的字段。这个差集检查现在成了棘轮（`字段闭环（批 8 补 29）`），
两个方向都管：**认识却不要**（字段永远空）、**要了却不认识**（模型白花钱，还会被算进 `dropped` 覆盖率）。

**B. 为什么 `region`/`time_of_day`/`features` 这三个最要命**

它们同时在 `STORY_INJECT_FIELDS` 里 —— 即 `finalPrompt` 会把它拼进画面描述、前端 `storyCardPhrase` 还会
在"实际发出"预览里逐字复算。也就是说**代码里早就承诺了"这两个字段会进图"**，
而模型从来不知道要抽它们 → 这两个位置**永远是空的**。补 17（地点/道具卡参考图）治的是"存下来没用上"，
这一条是它的**上游版本**：连存都没存下来。selftest 早就在用 `临江/夜晚/木质结构` 断言注入链能带这些字段
（说明机制没问题），缺的只是"向模型要"这一步 —— **断言覆盖了机制，却没覆盖"数据能不能到达机制"**。

**C. 两个真踩到的坑**

1. **写死的版本号钉**：apitest 里"本次改过的提示词版本已 bump 到 2"把 `2` 写死了，
   这一轮升到 v3 就红。版本号每轮都会涨，**钉要钉"≥2 且是整数"与"老版本指纹登记进历史表了"**
   （后者才是老库能升级的真正原因），别钉具体数字。
2. **拿"当前默认"去造"老库"**：验证升级路径时第一版 fixture 直接用 `DEFAULT_TEMPLATES` 的内容，
   于是造出来的"老库"内容已经是新版、指纹也是新版 —— 判成 `same`（本来就不用更新），
   却让我误以为"升级没生效"。第二版又用占位文本配旧指纹，还是错：**`superseded` 判据比的是
   `dig(content)`，不是行上的 `builtin_digest`**。最后用**线上库真实存在的 v2 正文**做 fixture 才对。
   教训：造"旧版本"fixture 必须用**真的旧内容**，别用现成默认值或占位文本糊弄 —— 否则测的是空气。

**D. 升级路径（补 28 机制的第一次实战）**

用真实 v2 正文造了两种老库形状，都实测升到 v3：① 补 28 **之前**装的（行上没有 `builtin_digest`）
→ 靠历史指纹表认出"还是官方那版"；② 补 28 **之后**装的（`builtin_digest` 自证）→ 靠自证。
外加一条"用户改过的"必须原样保留、并在横幅里点名。**三种情形全绿**。

**教训**：

1. **"机制存在"不等于"数据能到达机制"**：注入链有断言、字段也在 `CARD_FIELDS` 里，可模型从来不知道要抽它。
   凡是"两端各有一套字段表"的地方，都要有一条**对差集**的棘轮 —— 差集是静默的，两边各自都"看起来对"。
2. **钉要钉不变量，别钉快照**：版本号、数量、条数这类每轮都会变的值写进断言，就是给自己埋一颗定时红。
   钉"≥ 基线"、钉"关系成立"（如历史表里必须有上一版指纹），而不是钉"等于 2"。
3. **造旧版本 fixture 要用真的旧内容**：用现成默认值/占位文本造"老库"，会造出一个"本来就对"的库，
   于是你测的是空气 —— 而且它**看起来是绿的**（或红得莫名其妙），比没有测试更浪费时间。
4. **上游的洞比下游的洞值钱**：同一个"场景不一致"的病，补 17 治的是"存了没用"，这一条治的是"根本没存"。
   修上游时，先问一句"这个字段是从哪儿来的、有没有人真的向模型要过它"。

### 6.28 批 8 补 28 追加（提示词能更新 / 剧情卡人物闭环）

**A. 内置提示词的"更新"问题**

- **症状**：`seedTemplates` 只在"库里没有这个 key"时写入。改代码里的提示词，对**已经装过**的库完全无效，而且没有任何提示 —— 用户永远在用第一版提示词，我们每一轮的提示词改进都被这个洞吞掉。
- **判据**：一个内置模板行"是否还是我们发出去的那一版"，只能靠**内容**证明（不能靠 `updated_at`、更不能靠"用户没动过"的假设）：
  - `stored.builtin_digest === digest(stored.content)` —— 我们上次写进去的就是这个指纹，说明之后没人改过；
  - 或 `digest(stored.content) ∈ TEMPLATE_SUPERSEDED[key]` —— 本机制**上线之前**装的库，行上还没有 `builtin_digest`，只能靠历史指纹表认领。
- **安全底线**：两条都不满足 → **当成用户改过，原样保留**。覆盖用户改过的提示词是**不可逆**的伤害，而漏一次更新只是少一次改进（下次改了还会再遇到）。`keep` 带 `reason`（`same`/`custom`/`edited`），启动横幅据此**如实说出**"更新了几个、保留了哪几个" —— 不能默默不更新。
- **接线位置本身就是安全属性（本轮真踩到）**：播种会**写库**，最初写在模块顶层，于是**端口被别人占着时走 X4 分支退出的"影子实例"也会写一遍**。而 `persist` 是**整库快照全量写**：影子实例写进去的更新，会被正在跑的那个实例的下一次快照**覆盖掉**，两边都不报错。X4 防的正是"两个实例互踩、静默丢数据"，而 `poller.resume()` 本来就遵守"只在端口绑定成功后做副作用"这条纪律 —— 播种没有理由例外。现在播种移进 `listening` 回调（真机验证：同 HOME 同端口的第二个实例跑完后 `db.json` **逐字节未变**）。
  **边界（如实记录）**：**异端口同目录**的影子实例仍会起成 —— 端口守卫不是文件锁（README 已知边界，
  `tools/port-check.mjs` 场景 3 专门记录它）。那种情况下播种会写库，但这与 `poller.resume()` 等**所有**启动期副作用
  的行为一致，是既有边界、不是本机制引入的；本机制修的是 X4 明确要防的那一种（同端口影子实例被拒绝启动，
  却仍然写了库）。
- **测试怎么写**：判定逻辑抽成纯函数 `planTemplateSync(stored, defaults, {digest, superseded})`（注入点让离线断言能造"历史指纹"），六条判定路径在 selftest 逐条钉死；端到端在 apitest 里**另起一个独立 HOME 的实例**当"老用户"（两个 fixture：用户改过的必须原样保留、官方旧版必须被更新到新版），因为**影子实例根本不会走到播种**（那正是修正后的行为，另由 uitest 的位置钉守住）。

**B. `involved` 的闭环**

- **症状**：`involved` 被抽取（花模型调用）、被显示（`cardLine`/`beatLine` 的"涉及：…"），却**从来没有被任何逻辑读过** —— 没有一处检查那些名字是否真的存在。`STORY_INJECT_FIELDS` 里也没有 `plot`，`auditCards` 直接跳过剧情卡的字段。
- **后果**：剧情卡带着"涉及人物"进入分集大纲与剧本 → 剧本写到他 → 分镜里他出场 → 而外貌注入/角色绑定/参考图**全都落不到他身上**。同一个角色在不同镜头里换脸，链路上没有任何报错（与 `shot_char_unknown` 同类，但**发现得更早、更便宜**：镜头侧是在钱花完之后才报，卡片侧解析完就能报，而且改一张卡下游全部跟着对）。
- **判据（与镜头侧故意不同，两处都要说清）**：已知名字 = 人物卡（本名+别名）**∪** 角色库（本名+别名）—— 只算人物卡会把"用户在角色库里手建的角色"误报；只算角色库又会漏掉"还没入库的人物卡"，而后者恰恰是本体检要推动去补的那一步。比对时：整词命中算已知，**"词里包含已知名字"也算已知**（"顾寒的对峙"里含"顾寒"）。代价是"林晚秋"在存在"林晚"时会被漏报 —— 与 `bindNames` 的"宁可漏也不要错绑"一致，而**假警报比不检查更糟**（用户被刷两次就再也不看体检了）。泛称走 `UNKNOWN_NAME_STOP` 停用词表；**不把"没写"当"写错"**（空 `involved` 不报）。
- **聚合与出口**：按**名字**聚合（一个不存在的名字常被好几张剧情卡提到，逐卡报会刷屏），带 `card_ids`/`cards`/`near_names`（只给"互为子串"的候选 —— "写简称而库里有全名"是唯一真正有用的方向，能一眼解释清楚；不去猜拼音/编辑距离，**假建议比没建议更糟**），级别是 `info` 不是 `warn`（找不到 ≠ 错：可能是没抽到、可能是路人、可能确实写错了），`fixable:false` + `go` 走面板既有的「去处理」出口（不新增分支）。
- **预防与验收成对**：两个抽取提示词（`novel_extract` / `story_bible`）都写明"involved 只写本段/清单里出现过的**本名**、多个用顿号分隔、不写泛称、没有就留空" —— 提示词定死写法（预防），体检做验收（验收环），生效之后这一项应一直是空的。

**C. 补记指纹（`stamped`）——一个"只会在下一轮才炸"的陷阱**

本机制上线前装的库，行上**没有** `builtin_digest`。内容恰好等于当前默认的那些会被判成 `same`（不需要更新），
于是**永远拿不到指纹**；等到将来真改了这些提示词，"证明不了还是官方版"就会把它们判成 `edited` 而**永不更新** ——
除非维护者恰好记得手工往 `TEMPLATE_SUPERSEDED` 里补一条旧指纹。**这个坑不会在本轮报错，只会在下一轮静默吃掉改进。**
（真机上直接看到了：重启后 2 个被更新，**其余 14 个的 `builtin_digest` 仍是 `undefined`**。）
所以内容已经等于官方默认的行要**顺手补记指纹**，让它从今往后都能自证。
反向的红线同样重要：**绝不能**给 `edited`/`custom` 的行补记 —— 那等于把"用户改过的内容"登记成"官方内容"，
下次同步就会理直气壮地覆盖它，**把一个静默不更新变成静默丢数据**（对照 IG 专门钉这一条）。

**教训**：

1. **"只被显示、没被读取的字段"与"只被显示、没被读取的标记"是同一个病**（补 25 的 `edited` 是标记版，`involved` 是字段版）。凡是花模型调用抽出来的字段，都要有人读它、核它 —— 否则它只是让界面显得完整。
2. **会写用户数据的启动副作用必须放在"确认自己是唯一实例"之后**。这类 bug 不会报错、只会静默丢数据，而且**方向恰好相反**：看起来"多跑一次同步更保险"，实际是"多跑一次 = 覆盖别人的成果"。
3. **更新机制的安全性建立在"证明"而不是"假设"上**：证明不了"这一行还是我们发的"就不动它 —— 漏更新是可恢复的，覆盖人的劳动不可恢复。
4. **"这次不炸"不等于"以后不炸"**：补记指纹那条修的是**下一个版本**才会发生的失效。凡是"更新/迁移"类机制，
   都要问一句"这一轮跑完之后，数据处在**能自证**的状态吗" —— 只让当前这批数据看起来对，等于把问题推给未来。
5. **对照要"红得干净"**：本轮两个对照（IA/ID）第一次都让 selftest 以 `TypeError` **崩掉**而不是报红 —— 断言里直接写 `issues[0].x` / `keep[0].reason`，一旦被测行为被关掉，取字段就炸。崩掉虽然也证明"钉是敏感的"，但它**中止整轮**，让人看不出"到底哪几条钉在管这件事"。已改成取不到就给 `{}`，现在同样的对照给出**干净的失败清单**（IA 14 条、ID 3 条）。写断言时**取字段前先兜底**，让失败以"断言不成立"的形式呈现。

### 6.25 批 8 补 27 追加（"进程跑的是旧代码"防护）

- **"接口不存在"是最容易误导人的一句报错**：功能明明做了（`/api/story/plan` 早就在），
  但长驻进程跑的是三天前的代码 —— 用户看到的是"这功能根本没做"。**报错要说得出"你该做什么"**。
- **前端从磁盘读、后端只在启动时读一次**，这个不对称是根因：本项目是本地长驻服务 + 一轮一轮加功能，
  页面永远是最新的、接口永远停在启动那一刻。凡是长驻进程 + 热更新的组合都有这个坑。
- **防护不能把补救动作堵住**：X4（同目录第二实例拒绝启动，防两实例互踩丢数据）本身是对的，
  但它把"再启动一次"这个唯一的自救动作变成了"已在运行 → 退出"。**同一条分支要区分
  "同版本"与"旧代码"** —— 前者确实什么都不用做，后者必须点名该结束谁。
- **不让前端自己猜结论**：横幅读的是服务端给的 `code_stale`/`stale_files`（前端只是显示），
  与体检/过期体检同一条纪律：判定在一处，界面只搬运。
- **指纹按内容算，不按 mtime**：mtime 会被 `touch`、`cp -p`、`git checkout` 改掉而内容不变，
  拿 mtime 当判据会误报"代码变了"（那会让横幅变成狼来了）。SEA/exe 形态代码在二进制里，
  进程跑着不可能变 —— 显式短路，不做磁盘探测。
- **教训（与补 25 同一条，立刻又踩了一次）**：对照 HD 本该让"前端不渲染横幅"变红，结果 **0 红** ——
  断言里写的 `/renderStaleBar\(h\)/` 匹配到了**函数定义** `function renderStaleBar(h) {`，
  而不是**调用**。删掉调用它照样绿。**"绿"必须靠注入破坏证明过才算数**。

### 6.24 批 8 补 26 追加（逐段核对）

- **"按同一套参数切"不等于"切出来是同一段原文"**：`chunk_opts` 只锁住了参数，
  而对齐判据一直只比**段数**。追加解析是"先切 A、再切 B"，补抽/溯源是"重切整篇 A+B" ——
  接缝处必然不同，**而段数可能刚好相同**（1+1 = 2，实测逐段文本全不同）。
- **错的地方不止一处**：同一个 `aligned` 被**四个调用方**共用（补抽、溯源、章节、覆盖体检）。
  只修补抽是不够的 —— 溯源会把**错的段落**当成"这张卡的原文依据"，让一张正确的卡显得可疑
  （溯源的全部价值就是让人能核对，它骗人比没有更糟）。**一个判据一处实现，四处一起变对**。
- **拒绝要发生在"信结论"之前**：段号一旦对不上，`needs_retry`（靠 `chunk_states` 与卡片
  `evidence` 算出来的）本身就不可信 —— 所以对齐检查必须放在"算该补哪几段"**之前**，
  否则会先报"没有需要补抽的段落"（一句让人放心的话，而依据是坏的）。
- **指纹要能定位**：不能只说"对不上"，要逐段点出**第几段**；段数变少时**移位的段与消失的段**都要报。
- **追加的指纹必须按"先 A 后 B"接**：重切整篇的指纹不能覆盖它，否则等于把错的对齐当成对的记下来；
  已有指纹不完整（老原著）就**整份都不写** —— 残缺的指纹会让"没核对到"的段看起来像"核对过了"。
- **"不知道"仍然是独立的第三种状态**：没有指纹 → `verified:false`，退回段数判据并**如实说明**，
  与过期体检/覆盖体检同一条纪律（宁可说不知道，也不猜）。

### 6.23 批 8 补 25 追加（让"已改"真的有用）

- **只被显示、没被读取的标记等于没有**：`edited` 记了、界面也画了"已改"，
  但合并逻辑从没读过它 —— 于是那句"重新解析不会覆盖它"是**假承诺**。
  写进注释的承诺也必须由代码兑现（`retry-chunks` 的注释里还写着"永远不会把用户改好的卡片冲掉"）。
- **假承诺会和体检连成静默回环**：体检删掉撞名别名时标 `edited`，而合并的别名是并集 ——
  撞名问题会自己长回来。**"用户删掉的东西被并回来"是比"覆盖"更隐蔽的一类破坏**。
- **保护 ≠ 拒绝补全**：模型仍然可以补**空着**的字段（那是这个功能的价值），
  但已有值一律不动；`order`/`mentions`/`evidence` 是记账不是内容，照旧听新结果。
- **保护必须可见**："没被覆盖"和"被覆盖了却看不出来"在界面上长得一模一样，
  所以要报"保住了 N 张、是哪几张"，确认弹窗里也事先说明规则。
- **教训：断言可能"因错误的原因通过"**。端到端那条外貌钉一开始用"黑衣"（2 字），
  而 mock 对第 1 段返回的"白衣"也是 2 字 —— "更长者取胜"根本不触发，
  于是**把保护关掉它照样是绿的**（对照 FE 抓出来的）。测试值必须落在能真正触发规则的那一侧。

### 6.22 批 8 补 24 追加（多文件上传）

- **批量入口要把"顺序"当成一等公民**：一章一个文件时，**顺序错了原文就乱了**，而这件事只有用户能判断
  —— 所以不是"默默排好"，而是**把拼起来的顺序列出来**（含每个文件的字数），让错误看得见。
- **"排得动"的判据不能太窄**：一开始写的是"名字里一个数字都没有才提示"，
  可"第1章 + 序章"里序章该在最前还是最后**同样排不出来**（对照 EB）。判据改成"任何一个名字没有数字就点名"。
- **排序不能用 `localeCompare`**：一旦依赖运行环境 locale，同一批文件在不同机器上顺序不同 ——
  这种错极难发现（本地永远是对的）。自己实现"数字段按数值比"的键，结果可复现。
- **一个文件读不了就整体不落**：半份原文比没有更糟 —— 用户会以为全读进来了，
  而后面所有解析都建立在缺章的原文上。错误信息里必须**点名是哪个文件**。

### 6.21 批 8 补 23 追加（Word 文档读取）

- **边界要跟着事实改**：原来写"docx/pdf 是另一个数量级的依赖"，对 PDF 成立、对 .docx 不成立。
  把一条已经不准的理由留在文档里，下次就会拿它挡住一件其实很便宜的事。
  **反转边界时断言跟着改，不是删掉**（uitest 那条"docx 明确拒绝"改成了"接受 .docx + .pdf 仍拒绝且理由准确"）。
- **zip 的三个坑**：① **局部头的扩展域长度与中央目录里的可以不一样**（真实 .docx 常见：局部头带 UT 时间戳），
  拿中央目录的 extraLen 去算数据起点，读出来就是垃圾（对照 DC）；② **ZIP64 要明确拒绝** ——
  按 32 位读一个 ZIP64 文件会"成功"返回一堆乱码，比直接报错难查得多（对照 DA）；
  ③ 两种压缩方式都要覆盖，只测"存储"等于没测解压那条路。
- **实体解码顺序**：`&amp;` 必须**最后**解，否则 `&amp;lt;` 会变成 `<`（对照 DB）。
  这类"顺序错了一点点、看起来还能跑"的 bug，只有断言盯着真实输入才抓得到。
- **拒绝也要说人话**：损坏的 docx、不是 zip 的文件、没有正文的文档，各给一句能懂的话，
  而不是把异常抛到页面上（selftest 钉住"报人话而不是抛异常"）。

### 6.20 批 8 补 22 追加（章节复核）

- **只有张数等于没有信息**："第二章 3 张卡"判断不了抽得对不对。复核要能看到**是哪几张**、并且点得进原文。
- **张数与 id 列表同源**：分开算迟早分叉（界面上"3 张卡"却只列 2 张）。服务端只给 `card_ids`，
  张数由列表长度得出 —— 对照 CB 证明分开算真的会分叉。
- **章的原文开头要从这一章自己的标题开始**：块是 3000 字一装的，一章常常从块中间开始，
  拿块开头当章开头就会"点开第二章看到第一章的文字"。`assignChapters` 因此把每章在块内的起始位置
  （`starts`）暴露出来 —— 它与 `chars`/`spans` 用的是同一份 `bounds`，不可能对不上（对照 CA）。
- **"开关"与"给我看"是两种意图**：在主列表点自己那一行是开关（再点收起）；
  从章节复核面板点过来是"给我看"，把已展开的依据关掉会莫名其妙（对照 CC）。
- **不把"不知道"说成"没有"**：卡片列表还没加载时，章节面板会显示"这一章没有抽到卡片"——
  这是一句**假信息**。打开章节目录前先把卡片补上。

### 6.19 批 8 补 21 追加（章节识别与章节级溯源）

- **段号是实现的副产物，不是用户的语言**：切块按 3000 字一装，"第 34 段"对作者毫无意义。
  出处必须翻译成"第几章"，否则补 20 做的溯源仍然要用户自己数。
- **标题识别只认整行**：正文里回指章节（"他翻开第十二章的书页……"）是常态，用子串匹配会把正文当标题。
- **目录页是最大的假阳性来源**，用"与下一个候选挨得太近"滤掉，并**如实上报滤了几个** ——
  不假装原文只有一章（与"宁可说不知道，也不猜"同一条纪律，对照 BU）。
- **映射不用偏移量**：块是段落拼起来的、与原文未必逐字对齐，偏移一漂就把整章对错；
  标题是有辨识度的字符串，直接找更稳。一块可能横跨两章，所以给 `spans` 如实说明（对照 BT）。
- **"避免重复计数"曾经让我把问题报在错的章上**：改成"只记主导章"后，标记在第二章的那一段
  因为块的主导章是第一章，目录里报的是第一章 —— 用户去第一章什么也找不到。**假定位比不定位更糟**。
  结论：**"定位问题"和"给卡片贴出处"是两个问题** —— 出处要唯一（用主导章），问题要能定位（凡涉及的章都报）。
- **出处放在卡片本体上，不放编辑表单里**：核对要随手可做；藏在编辑态里等于没有（BZ 对照也证明了
  不预取章节映射时出处会退回段号，所以映射必须在**渲染之前**拿到）。

### 6.18 批 8 补 20 追加（卡片溯源）

- **不可核对的抽取等于要求用户盲信**：卡片是整条链的地基，而界面上只有"证据段 3"这种段号。
  想核对就得自己回原文里数段 —— 成本高到没人会做，于是错卡一路传到剧本、分镜、图。
  把原文片段直接摆出来，"核对"才是一件顺手的事。
- **服务端只切分、不拼 HTML**：命中的词来自**模型输出**，服务端拼标签就是把模型输出注进页面。
  所以 `markTerms` 返回 `{t, hit}` 纯文本片段，前端逐个 `esc` 后再决定包不包 `<mark>`
  （匹配逻辑一份实现、可离线断言；前端只负责转义与包裹，对照 BR）。
- **截断要如实说**：分块可能几千字，整段倒给用户等于让他自己找；但截了就必须说"前后还有内容"，
  不能让用户以为这就是完整段落（与"宁可说不知道，也不猜"同一条纪律，对照 BQ）。
- **多余的代码要删掉，不要留着当"防御"**：本轮原本按词长排序（注释还写着"否则会切碎"），
  但对照 BS 显示把排序改成短词优先结果**完全不变** —— 真正保证结果的是区间合并。
  留着它会让下一个人以为它在起作用，改坏了也看不出来。**测不出来的"防御"就是负债**，故删除，
  并把钉子改成"结果与词的先后无关"（这个不变量是真的、且可证伪）。
- **溯源能力有自己的前提，要一并钉住**：`source_id` 是**来源事实**、白名单外改不动；
  删除原著会**级联删卡片**（否则留下"指不到原文的孤儿卡"，溯源自己先断）。
  两条都用 apitest 钉住 —— 它们是"卡片总能回到原文"这个承诺的地基。

### 6.17 批 8 补 19 追加（参考图缺口体检）

- **"能力接上了"不等于"有人在用"**：补 13/补 17 把参考图接进了出图调用，但没有任何地方会问
  "该挂的挂了吗"。一个场景在 20 个镜头里反复出现、一张参考图都没挂 → 20 张图长得都不一样，
  而**每张图单独看都是"成功"**。这类不一致最难靠肉眼发现，所以必须机器点名。
- **体检的第一要务是不制造噪音**（与补 18 同一条纪律，方向相反）：只报**会重复出现**的
  （≥2 个镜头 —— 只出现一次的道具不值得为它准备参考图），只报**真的会进图**的类型
  （给信息卡挂图本来就没用）。报得越宽，用户越早学会无视整张报告（对照 BM）。
- **"挂了但用不上"比"没挂"更危险**：用户挂的是本地文件（`/assets/…`），上游按 URL 取图抓不到 ——
  他以为自己已经做完了，于是**不会再去看**。所以"没挂"与"用不上"必须分开报（后者说清几张、为什么）。
- **判定必须由调用方注入解析器**：卡片上存的是**图片 id**，能不能用只有查过图库才知道。
  纯函数拿 id 当 URL 判，会把已经配好的卡片全部误报成"用不上" —— 这种假警报比不检查更糟，
  因为用户会照着去改本来正确的东西（对照 BN，这个错误是本轮实现时真犯过的）。
- **体检不能只有结论、没有出口**：挑哪张参考图是人的判断，机器替不了，所以 `fixable` 是 `false`；
  但问题项带 `go`（去哪个页面、定位哪个对象），面板给「去处理」并高亮目标卡片 ——
  否则用户读完报告还得自己猜该去哪一页找哪一张卡。
- **跨页跳转的参数名要对得上**：原著页读 `project_id`/`source_id`，角色库页读 `project`；
  而且**原著页只在 URL 有 `source_id` 时才加载卡片列表** —— 只给 `project_id` + `card_id`
  会落到一个空工作台上（浏览器契约测试抓到的真 bug）。
- **本轮最贵的一课**：给原著页加"跳进来定位卡片"时，把新代码插进了 `if (sourceId) … else …` 中间，
  `else` 于是挂到了 `focusCardId` 上 —— 结果**每次正常打开原著页**都会用"还没有选中原著"
  盖掉刚加载出来的卡片。语法检查过、selftest/uitest/apitest 全绿，只有真机浏览器测试抓到。
  这不是"测试不够"，而是**共享前端改动必须过真机**这条纪律的又一次实证（见 AGENTS.md 注意事项 9）。

### 6.16 批 8 补 18 追加（抽取覆盖体检与补抽）

- **"失败"这个词一旦混装两件事，它就等于没有信息**：模型明确说"这段没信息"是**正常结局**，
  而"模型返回了条目却被我们丢掉"是**真丢数据**。两者都表现为"这段没有卡片"，
  但前者不该打扰用户、后者必须让人看见。混成一个"失败 N 段"的后果不是漏报，
  而是**告警疲劳**：用户学会无视它，于是真丢的那次也一起被无视（对照 BI/BJ）。
- **判据要用纯事实，不要猜**：`raw_count`（模型给了几条）与 `card_count`（我们接住几条）一比，
  四种结局就分开了，不需要再问一次模型，也不需要写启发式（`classifyChunk`）。
- **只说"丢了几条"用户没法动手修**：要报出**模型给的原始类别**（`raw_kinds`），
  用户才知道是"类别不在六类里"还是"名字为空"（对照：`npc` 这类就是该扩类别或改名字）。
- **报告必须带出口，否则是死胡同**：面板列出"哪几段该补抽"的同时给一个能点的补抽按钮，
  并且**解析完自动把面板打开** —— 修掉原来那句"可在卡片列表重试"的**假承诺**（列表里根本没有重试入口）。
- **重新切块是补抽的隐形地雷**：补抽要按第 N 段重跑，就必须按**解析时那套分块参数**重新切块；
  用默认参数切出来段数不一样，"补抽第 5 段"会把**另一段原文**当成第 5 段重抽，而用户看到的是"补抽成功"。
  所以分块参数**留档**（`chunk_opts`），且切不回原样就**拒绝动手并说清原因**（对照：宁可报错也不重抽错的原文）。
- **老数据要能体检，但不能替模型回答**：本轮之前的原著没有逐块记录，只能看出"哪些段没有卡片"，
  于是标 `unknown`（不是 `empty`，也不是 `failed`）并列进补抽候选 —— 补抽只补不删，所以候选是安全的。
  这与过期体检的 `unknown` 是同一条纪律：**宁可说不知道，也不猜**。
- **只补不删要用 id 证明，不能用张数**："删了重建"也能凑出一样的张数，但 id 一变，
  分镜绑定与界面状态就全指向不存在的卡（批 8 补 10 修过的坑）。断言必须落在 id 上（对照 BL）。

### 6.15 批 8 补 17 追加（地点卡/道具卡参考图进出图输入）

- **"存下来 ≠ 用上了"这个坑会反复出现**：批 8 补 13 修的是角色参考图从不进调用，
  本轮是**同一类**——地点/道具卡连"存"的地方都没有，只有一行文字，于是"同一个客厅"每张图都不一样。
  每加一个"可视化载体"字段，都要问一句：**谁在读它？**
- **用户挂的数据不能被归并冲掉**：`store.update` 是 `Object.assign` 合并，所以**键不在 patch 里就保留**。
  `normalizeCard` 一旦在字段缺失时吐一个 `[]`，重新解析/追加解析就会把用户挂的图静默清空 ——
  所以它**故意不产出**这个字段（对照 BG 钉死形状，不是钉值）。
- **多个来源抢同一个上限时，顺序就是产品决策**：总上限 4 张，**脸比景更难靠文字说准**，所以角色优先；
  被挤掉的必须如实计数（对照 BH），否则"我挂了 6 张怎么只用了 4 张"没人回答。
- **花钱前的预检要覆盖所有来源**：只算角色不算场景，那句"带了几张"就是假的。
- **一句话的注释也可能骗过文本棘轮**：`normalizeCard` 里解释"为什么不产出这个字段"的注释必然写出字段名，
  于是被自己的钉子判红。凡按文本匹配的棘轮，都要**先剥注释再判**（本轮第二次踩到，已抽成统一做法）。

### 6.14 批 8 补 16 追加（全链路进度体检）

- **"半成品状态"也要有人报**：解析完卡片没分集、3 集骨架只写了 2 集剧本、20 个镜头只出了 5 张图 ——
  这些都不是错误，但都需要有人告诉用户下一步做什么。**不报 = 用户自己拼 = 漏做**。
- **`blocked` 与 `todo` 必须分开**：前者是"前置还没做，点进去也做不了"，后者是"轮到你了"。
  混成一个"待办"，用户会照着点却发现按钮是灰的 —— **报状态就要报到能照着做的粒度**。
- **进度要按"集"而不是按"条"算**：同一集重生成会存多条剧本，按条数算分母会虚高，
  于是"3 集骨架只有 2 集剧本"被显示成"已完成"。**分母的口径要和用户的心里口径一致**（对照 BC）。
- **每段的分母是下一段的实际需求**：出图段的 need 是**镜头数**，不是"有没有分镜" ——
  把"有分镜"当成"有图"，那一段就永远打勾，用户以为图都出好了（对照 BD）。
- **直达要带上项目**：面板上已经选好了项目，点"下一步"再到那一页重选一次是纯浪费。

### 6.13 批 8 补 15 追加（逐集分镜用上过期体检）

- **防护机制会变成陷阱**：跳过"已有分镜的集"是对的（防翻倍），但判据只看"有没有"、没看"还算不算数"，
  于是**最需要重跑的那几集永远跑不到**。凡是"跳过/去重/缓存"类判据，都要问一句它依赖的前提现在还成立吗。
- **同一个体检要在每个消费点都用上**：补 12 只接了故事脚本页 —— 能力做出来不等于能力被用上（同批 8 补 13 的教训）。
- **清空按项目 + 集限定**（服务端已强制两个参数），前端复用同一条纪律，不自己拼删除条件。
- **"删了又生成"必须如实上报**：否则汇总里看起来什么都没发生。

### 6.12 批 8 补 14 追加（负面提示词并入出图提示词）

- **同一份行数据被多个链路消费时，逐个消费方核对**：`negative_prompt` 视频读、图片不读，界面照常显示 ——
  这类"半个字段"的缺口比全缺更难发现。
- **绝不单发网关不认的字段**：并入正向提示词是用弱一点的效果换"不打断出图"；理由要写进注释，别让后人"顺手加上"。
- **测试替身必须与真实网关一样严格**：mock 照单全收 → "单发不合法字段"永远测不出来（对照 AU 的假绿）。
  凡是"真实上游会硬拒"的约束，mock 里都要有一份。
- **放宽判据只能针对已知变量**：组合断言加 `negless()` 只剥那一个已知后缀，出现别的尾巴要让它红出来。

### 6.11 批 8 补 13 追加（角色参考图进出图输入）

- **字段存在 ≠ 能力存在**：`reference_image_ids` 有类型、有界面、有校验，唯独没有消费方。
  每处单独看都正常，合起来就是"参考图白传了"。检查清单里要专门有一条：**新字段谁在读**。
- **与既有的降级判定保持同一套**：Agnes 只能抓公网 URL（图生视频早就是这个判据），参考图沿用同一判定与话术，
  用户不必学两套规则；用不上时**必须说**，否则等于承诺了没兑现。
- **上限要双向一致**：collect 侧与最终数组都要夹；`used` 必须等于**实际发出**的张数。
- **溯源记"实际发出"**：`generation_tasks` 记的是喂进模型的完整输入，不是调用方传了什么。

### 6.10 批 8 补 12 追加（剧本/分镜的过期体检）

- **生成是要花钱的，所以"该不该重生成"必须能免费反复看**：与体检/分集同一条纪律 —— 纯本地、零模型调用。
- **三种状态要分清，尤其是"不知道"**：`ok` / `stale` / `unknown`（没有指纹）。把 `unknown` 当 `ok` 会让用户
  以为没问题，当 `stale` 会让他白花钱重跑一遍 —— 所以它单独计数，且**不计入"该重生成"**（对照 AN）。
- **指纹要如实描述"实际喂了什么"**：前情是从更早的集推出来的，必须进指纹（对照 AM）；
  显式声明"不带前情"时前情变化又不该影响指纹 —— 同一份算法要能吃下这两种情况。
- **精确性就是省下的钱**：往后追加章节不该让前面的集报过期（拍表与前情都没变）。
- **指纹只留一份实现**：`episodeInputDigest` 由服务端返回给前端存，分镜的 `script_digest` 由服务端按入库
  那一刻的正文算 —— 前端复算哈希迟早漂移，而判据本身是"内容变没变"。
- **默认动作要跟着体检走**：逐集生成的默认范围 = "缺剧本或已过期"的那几集，用户想全跑就自己改范围。

### 6.9 批 8 补 11 追加（人物卡 ↔ 资产库漂移）

- **"同一份数据的两面"最容易各走各的**：人物卡是原著读到的，资产库那份是出图真正注入的。
  `cardToCharacter` 复制过去之后没有回头路 —— 追加解析补全了卡，库里还是旧样子，
  **界面显示新描述、出图用旧长相，而且没有任何报错**。体检 + 同步把这条闭环补上。
- **判据只看会注入提示词的字段**（外貌/服饰/别名）：`characterPhrase` 与名字匹配真正用到的就这些。
  把 role/personality 算进来会让每张卡都报（对照 AL：6 红）。
- **"只补空"与"覆盖已有"分开定级**：空 → info（纯补全）；非空且不同 → warn + 逐条列出"库值 → 卡值"。
  哪份对是人的判断，机器只发现与搬运（对照 AJ）。
- **同步绝不碰人的编辑**：只写外貌/服饰/别名，role/gender/age/personality 一律不动（对照 AK）。
- **注入对照前先断言锚点唯一**：`const patch = {};` 在 `routes.js` 里出现 11 次，`replace(...,1)` 会改到
  第一个匹配（另一个端点）—— 结果是 apitest 在无关处崩掉，**看起来像改动引发了别的故障**。
  现在注入脚本一律 `assert s.count(a) == 1`。

### 6.8 批 8 补 10 追加（追加解析与归并 id 稳定）

- **连载场景的成本纪律**：只解析新增章节。两条判据缺一不可 —— 调用次数 = 新增段数 + 1，
  **且发给模型的正文里没有旧章节**（次数可能因为并发/重试而巧合，正文不会）。
- **块号接着排**：新卡的 `evidence/chunk_index` 必须落在新增区间；断言用**库里读回来的卡**，
  不用返回体里自己算的 offset（自证不算证据）。
- **顺带修掉一个一直在的坑**：归并原来是"删光 origin=bible 再重建"，语义上没错（替换而非叠加），
  但每次归并都换一批 id —— 分镜绑定、体检 target_id、界面状态全部指向不存在的卡。
  改成按 kind+名字就地 upsert，**替换语义不变、id 稳定**。对照 AI 把这件事钉住了。
- **钉子的健壮性也是质量**：`byName()` 找不到就 `undefined.order` → 整份 selftest 崩掉，
  只看到一条 TypeError、看不到失败范围。崩溃安全的写法（返回 `{}`）让对照 AH 报出 7 条红。

### 6.7 批 8 补 9 追加（逐集生成分镜）

- **全链路到此闭环**：原著 → 卡片 → 分集骨架 → 逐集剧本 → **逐集分镜**，全程不需要人工搬运文本。
- **共用内核 > 两处各写一份**：`shotsFromText(text, ep)` 是单集生成与逐集生成的唯一实现。
  收益在对照 AG 里看得很清楚：改错一处字段映射，两条路一起红。
- **"不会翻倍"是本条功能的硬要求**：跳过判据必须**按整部剧**统计（页面的 `rows` 只有当前集），
  否则重跑会把别的集翻倍 —— 对照 AF 用 `calls: 2` 与"镜头 3→6"证明了这条钉子真的在守。
- **报数分两处**：逐集结果在进度条、汇总在 toast；断言"报数了"要两处都读。

### 6.6 批 8 补 8 追加（前情提要 + 逐集生成）

- **长篇连续性的零成本做法**：每集生成时把**前面几集**的拍表带进请求体（本地分集骨架算，不额外调模型）。
  预算超了从**最早**的一端丢（越近越相关），并如实上报省了哪几集 —— 用户要能判断这份前情够不够。
- **"连续性"的判据是请求体**：browser-test 断言真的发出去的 user message 里有前情与本集拍表，
  而不是断言界面上出现了"已载入"的提示条。
- **批量生成的三条纪律**（沿用本项目既有做法）：先确认次数（花钱的事先说清）、失败只丢这一集（不能因为第 7 集
  坏 JSON 就把 8〜20 集一起丢掉）、可取消（已生成的保留、没轮到的绝不调用）。
- **两个只有真机才看得见的坑**：共享模块 `api.js` 插错位置 → 整个壳层白屏（selftest/uitest 全绿、browser-test
  pass=0）；`qs is not defined`（api.js 没有这个助手）→ 语法合法、只在运行时抛，表现为"按钮点了没反应"，
  靠 `window.__uiRejects` 定位。**结论：共享模块的改动必须过真机，文本断言挡不住这一类。**
- **测试自身的坑**：用 API 现建的项目不在壳层 `state.projects` 里 → 路由判"项目不存在"并切到别的项目，
  后面所有断言都在另一个项目上跑。新建项目后要 `Page.reload`。

### 6.5 批 8 补 7 追加（画风写死与注入边界）

- **"界面真正消费的字段"才是契约**（对照 AC）：体检返回三组问题（`card_issues` / `shot_issues` / `style_issues`）
  和一个合并后的 `issues`，**面板渲染的是 `issues`**。第一版断言全写在分组字段上，于是"忘了并进 issues"
  这个致命 bug 让 apitest 全绿、真机上一条问题都不显示。补钉时还要注意**位置**：等式钉放在"确实存在问题"之前，
  分组数组是空的，等式恒成立、钉不住任何东西 —— 这类"钉在空集合上"的假阳性比没钉更危险。
- **词表与画风表同源（跨文件棘轮）**：`STYLE_WORDS` 覆盖 `ART_STYLE_MAP` 的每一个值由 selftest 逐条验证。
  画风表加新风格而词表没跟上，立刻红 —— 否则"新画风写死在提示词里"会静默漏检。
- **预防与检测成对（延续补 6 的模式）**：补提示词的 LLM 链写清三条禁令（画风 / 长相 / 中文人名），
  体检用 `shot_style_baked`（画风）与 `shot_char_unlocked`（名字）验收。
- **两条测试自身的坑**（已写进 `AGENTS.md`）：同页同参再设一次 hash 不触发路由（页面继续用旧数据，
  要 `Page.reload`）；静态按钮先于数据出现（等待条件要等行、不能等按钮）。

### 6.4 批 8 补 6 追加（角色名册）

- **预防与检测成对**：名册（预防）让模型照着本名写；`shot_char_unknown`（检测）把"角色库里找不到的名字"点出来。
  只有预防没有检测，就无法知道名册是否真的生效（模型可能照样自由发挥）；只有检测没有预防，用户只能事后一个个改。
- **长相不进提示词**：名册只给名字与一行"把握形象"的参考，并明确禁止写进 `image_prompt/video_prompt`。
  理由有两条：① 使用点还会注入一次长相，写两遍不一致就换脸；② 名字一旦出现在提示词里，未锁定角色会被
  `characterPhrase` 直接跳过（既有语义）。这两条都由 browser-test 钉住（对照 Z）。
- **"名册真的到了模型面前"是可证的**：browser-test 的 mock **从真实请求体里把名册抠出来**，
  再用抠出来的本名回一个分镜表 —— 只有名册真的进了请求体，后面"自动绑定命中"才可能发生。
  这比"我在源码里拼了这个字符串"强一层（源码级钉只能证明我写过，不能证明它发出去了）。
- **等待条件必须与被测事实解耦**：原来等"页面出现本名"，名册一失效就先超时（对照 Y 第一次跑就是这个形态），
  精确断言没机会报。改成等"分镜行出现"之后，对照 Y 报出的才是那两条断言。这是写契约测试的一条通用经验。

### 6.3 批 8 补 5 追加（镜头绑定自动匹配）

- **四层证据**：selftest 33 钉（纯函数：可匹配名口径 / 两档置信度 / 长名罩短名 / 别名 / 单字名不匹配 /
  已绑定不重复 / 非可注入类别过滤 / 按目标聚合与计数）+ apitest 49 钉（端点：**不调模型**、干跑不落库、
  strong_only 不猜、并集不覆盖、幂等、按 storyboard_ids/episode 限定范围、缺参 400、按目标修复与锁定幂等、
  人物卡当目标 400、修复也不花钱）+ uitest 14 钉（入口与按钮、干跑确认、生成后自动绑、并集写法、
  问题码/动作码分离、确认文案）+ browser-test 12 钉（真机：干跑弹窗列出镜头与名字并标出推断项 → 确认落库 →
  手工加的镜头被体检兜住 → 按目标修复真的写进后端）。
- **`code` 与 `fix_code` 分离**（对照 X）：这是本轮唯一一个**源码级钉全绿、真机契约才抓到**的 bug ——

### 6.2 批 8 补 4 追加（分集大纲骨架）

- **三层证据**：selftest 46 钉（纯函数：空输入 / 纯计数切分 / 幕次收口 / 硬上限与 forced 上报 / mixed 覆盖 /
  参数钳制 / 拍序按 order / 一拍一行的字段口径 / 骨架文本的四个小节与"不出现空标题"）+
  apitest 29 钉（端点：**一次模型都不调**、形状、按幕收口、下限真的生效、非法参数回落、来源隔离、空项目如实为空）+
  uitest 13 钉（入口与容器、api 路径、handler 体不含模型调用、下限可调、复制/带入、BASIS_LABEL 三态、
  scripts 侧认 `outline` 并传 `['plot']`）+ browser-test 11 钉（真机：默认切 2 集 → 下限调 5 重切成 1 集 →
  带入落到「本集大纲」→ URL 参数被抹掉）。
- **为什么"每集至少 N 拍"这个措辞很关键**：按幕收口会给出"多于下限"的结果（下限 3 时第一集 4 拍，因为它在"合"处收口）。
  如果 UI 写「每集 N 拍」，用户会以为工具没听懂；写「每集**至少** N 拍」并把"幕次覆盖 8/8""优先落在合/起处"写在面板上，
  结果就变成可解释的。这类"把算法语义如实翻译给用户"的措辞，和体检里"不替用户决定冲突值"是同一条纪律。
- **`perEpisode` 的语义边界用钉锁死**：0 / 负数 / 非数字 → 回落默认 4（否则会切出"每集 0 拍"的死循环或空集）；
  超过 20 钳到 20（再大就不是分集而是"一次说完"）；小数四舍五入。这三条都有 selftest + apitest 双份钉。

### 6.1 批 8 补 3 追加（一致性体检）

- **体检链的两层证据**：selftest 43 钉（纯函数：同名/别名撞名/缺字段/不误报/合并语义/计数口径）+
  apitest 36 钉（端点：**一次模型都不调**、别名修复、入库幂等、合并改指、参数校验、修复也不花钱）+
  uitest 11 钉（入口与容器、端点路径、handler 体不含模型调用、合并前必须确认、冲突值必须告知、修复后重跑）+
  browser-test 12 钉（干净不报 → 两来源同名必报 → 确认弹窗 → 合并真生效；外加卡片删除按钮的真机契约）。
- **两表一致钉**：注入用的表在 `lib/routes.js`（`STORY_CARD_INJECT_FIELDS`，前端 `consts.js` 逐字镜像），
  体检用的表在 `lib/story.js`（`STORY_INJECT_FIELDS`）—— 两张表必须逐项一致，否则会出现
  "体检说这项能注入、实际不注入"的鬼话。selftest 有专门一条 deepEqual 钉。
- **ui-audit 加"内联面板动作"**：此前只有"开弹窗"一种钩子，体检报告是**内联面板**不是弹窗，于是它的布局
  （变长的问题标题 + 徽标 + 修复按钮三列）在 4 个视口下是盲区。现在钩子支持 `{requireModal:false}`：
  不等弹窗，但要求"面板里真的有字"，否则报一条"内联动作无产出"（正向对照 Q：改坏入口选择器 → 4 视口各报一条）。
  种子同时塞了三张卡（同名地点卡 / 缺描述地点卡 / 没外貌人物卡），让面板落在"要处理 + 可优化 + 可修复 + 不可修复"
  四种行都有的真实密度上，而不是量一个空态。
- **`dataOf` 通用棘轮**：`ui.js` 的 `dataOf` 是**字面**取属性，驼峰写法恒为 `null` 且**不报错**。
  批 8 下的卡片删除按钮（`data-del-card` vs `'delCard'`）与批 8 补 3 的体检修复按钮（`data-audit-fix` vs `'auditFix'`）
  各踩一次。现在 uitest 逐页比对"每个 `dataOf` 读的名字都被渲染过"，并用真机契约锁住"两击删除真的会删"。

- **对照过程中发现的两个真问题**（已修，见 `docs/issues.md` B62）：
  1. **计费钉本来是假的**：`plan` 是同步 handler，不可能 `await` 调模型，
     所以"立刻数调用次数"这条钉只能证明"没有同步调用"——等于什么都没证明。
     加上 `sleep(400)` 后，对照 F 才真的能抓到"忘了 await 的偷偷调用"。
  2. **页面白屏且零报错**：`novel.js` 曾自建容器（`createElement('div')` + `className='page'`）当页面根，

     只有浏览器测试报"等待超时"。已加 uitest 棘轮钉死"首参必须是 container、不得自建 .page 容器"。
  3. **测试原文太短**：五幕之前只有 236 字，`minChars=400` 的尾块合并把整篇并成 **1 块**，

     加长到 834 字后才真正切出 4 块。
